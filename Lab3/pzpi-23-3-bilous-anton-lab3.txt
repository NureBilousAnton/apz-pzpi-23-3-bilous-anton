                              2 МЕТА РОБОТИ

     Розробити клієнтський SPA-застосунок для системи розумного освітлення
LumiRum.   Застосунок   має   забезпечувати   роботу   клієнтів   у   веб-режимі,
підтримувати окремі інтерфейси для звичайних користувачів і адміністраторів,
реалізовувати інтернаціоналізацію (українська та англійська мови), а також
функціонал резервного копіювання та відновлення даних через експорт і імпорт у
форматі JSON.

                           3 ОПИС ВИКОНАНОЇ РОБОТИ

      3.1 Архітектурні рішення

      Web-застосунок реалізовано як Single Page Application (SPA) на базі
бібліотеки React 18 з мовою TypeScript та інструментом збірки Vite. Застосунок
взаємодіє з серверною частиною LumiRum через REST API за допомогою HTTP-
проксі Vite у режимі розробки, що усуває необхідність налаштування CORS на
сервері.
      Архітектура застосунку розподілена на такі шари:
      а)   API-шар («src/api/») – відповідає за всі HTTP-запити:
           1)   «client.ts» – екземпляр axios з перехоплювачем запитів (додає
                заголовок «Authorization: Bearer») та перехоплювачем відповідей
                (обробляє статус 401: очищує стан авторизації і перенаправляє на
                сторінку входу через зареєстрований зворотний виклик);
           2)   «errors.ts» – функція «apiErrorMessage», що розбирає структуроване
                тіло помилки сервера «{ "error": { "code": "...", "message": "..." } }» і
                відображає відомі коди на зрозумілі повідомлення; функція-обгортка
                «safeApiCall<T>» повертає дискриміноване об’єднання «{ data, error:
                null } | { data: null, error: string }»;
           3)   Файли «auth.ts», «devices.ts», «profiles.ts», «telemetry.ts», «users.ts»,
                «admin.ts» – типізовані функції для кожної кінцевої точки API.
      б)   Шар типів («src/types/») – TypeScript-інтерфейси, що відповідають
           схемам OpenAPI: «Device», «Profile», «Telemetry», «LightingSchedule»,
           «User»,     «AuthResponse»        тощо.         Тип   «Role»   змодельовано   як
           дискриміноване об’єднання: «"admin" | "owner" | { user: number }», що
           відповідає форматам серверного JSON.
      в)   Стан авторизації («src/store/») – Zustand-сховище зі збереженням стану
           в «localStorage». Зберігає JWT-токен і поточного користувача між
           сесіями. При зверненні до сховища з компонентів використовуються
           окремі селектори для кожного поля, щоб уникнути нескінченного циклу
           повторного рендерингу.
                                                                               5
     г)   Шар хуків («src/hooks/») – TanStack Query (React Query v5) надає
          кешування серверного стану, автоматичне оновлення та скидання кешу
          після операцій зміни даних.
     д)   Шар представлення («src/pages/», «src/components/») – маршрутизація
          через React Router v6; кожна сторінка є функціональним компонентом,
          що використовує «useQuery»/«useMutation» для роботи з даними. Форми
          реалізовані через «react-hook-form» з валідацією схем «zod».
     Технологічний стек:
      –   React 18 + TypeScript + Vite
      –   Mantine v7 (компоненти, сповіщення, модальні вікна, вибір дат)
      –   TanStack Query v5 (серверний стан)
      –   React Router v6 (маршрутизація)
      –   axios (HTTP-клієнт)
      –   Zustand (клієнтський стан авторизації)
      –   react-hook-form + zod (форми та валідація)
      –   Recharts (графіки телеметрії та розкладу освітлення)
      –   react-i18next (інтернаціоналізація)
      –   dayjs (форматування дат)

     3.2 Взаємодія з системою

     Застосунок підключається до серверної частини LumiRum через REST API.
JWT-токен зберігається в «localStorage» через Zustand-сховище і автоматично
додається до кожного запиту axios-перехоплювачем. При отриманні статусу 401
перехоплювач відповіді викликає зареєстрований зворотний виклик, що очищує
стан авторизації і перенаправляє на сторінку входу, не вимагаючи обробки цього
випадку на рівні кожної сторінки окремо.
     Функціональність застосунку охоплює:
      –   Автентифікація та реєстрація – вхід в систему та самостійна реєстрація
          облікового запису типу Owner;
      –   Пристрої – перегляд, створення, редагування та видалення IoT-пристроїв;
          відображення версії прошивки, відносного часу останньої активності,
                                                                                   6
             статусу видимості; керування секретним ключем пристрою (перегляд,
             копіювання, перегенерація);
         –   Профілі – перегляд власних та спільних профілів; створення, редагування
             та видалення власних; перегляд спільних профілів інших власників у
             режимі читання;
         –   Розклад освітлення – лінійний графік температури кольору впродовж
             доби (96 точок по 15 хвилин), побудований на Recharts із форматуванням
             часової осі;
         –   Телеметрія – перегляд даних пристрою у вигляді графіка або
             таблиці; на графіку три серії (яскравість, температура кольору,
             навколишнє освітлення) відображаються на незалежних осях Y через
             «ComposedChart» з кількома «YAxis», оскільки одиниці вимірювання
             несумісні; фільтрація за діапазоном дат; видалення телеметрії за
             діапазоном;
         –   Управління акаунтом – зміна логіну та пароля, вихід із системи,
             видалення акаунту, створення підкористувачів (для Owner);
         –   Панель адміністратора – перевірка стану сервера, перегляд статистики
             системи, пошук та видалення користувачів (для Admin);
         –   Експорт та імпорт даних – збереження JSON-файлу з профілями та
             пристроями поточного користувача; вибір файлу для імпорту на сторінці
             акаунту з попереднім переглядом та послідовним застосуванням: профілі
             та пристрої зіставляються з наявними за іменем – знайдені оновлюються,
             відсутні створюються.
        Формат експортованого JSON:

1   {
2       "version": 1,
3       "exported_at": "<ISO timestamp>",
4       "profiles": [{"name": "...", "timezone": "...", ...}],
5       "devices": [{"name": "...", "profile_name": "...", "is_public": true}]
6   }


        Поля, згенеровані сервером («id», «owner_id», «secret_key», «created_at»), не
включаються до експорту. Замість «profile_id» використовується «profile_name» –
це забезпечує переносимість файлу між акаунтами.

                                4 ВИСНОВОК

     В ході лабораторної роботи розроблено web-застосунок для системи
розумного освітлення LumiRum у вигляді Single Page Application на базі React 18
з TypeScript. Застосунок реалізує повну взаємодію з серверною частиною через
REST API, забезпечує підтримку двох мов інтерфейсу (англійська та українська)
та розмежування доступу відповідно до ролей користувача (Owner, Admin).
Реалізовано функціонал керування пристроями, профілями освітлення, телеметрією
з багатоосьовими графіками, а також унікальну для web-клієнта можливість
експорту та імпорту налаштувань у форматі JSON із зіставленням за іменем.

      Запит 3. При завантаженні сторінки акаунту відображається порожній екран.
Крім того, у таблиці пристроїв остання колонка має заголовок «—» замість назви.
Після навігації назад у консолі браузера з’являється необроблена JSON-помилка про
відсутність автентифікації.
      Відповідь 3. Виявлено три помилки. По-перше, встановлений пакет
«@mantine/modals» мав версію 9.x замість 7.x, що відповідає решті пакетів
Mantine – несумісність спричиняла збій під час рендерингу. По-друге, заголовок
колонки видимості використовував ключ «common.notAvailable» («—») замість
«devices.visibility». По-третє, запит «listUsers» викликався для користувачів з роллю
Owner, однак маршрут «/users» вимагає ролі Admin – отримана відповідь 401
спрацьовувала перехоплювач і виконувала вихід із системи.
      —
      Запит 4. Сторінка акаунту досі відображає порожній екран навіть після
попередніх виправлень, і навіть для адміністраторів.
      Відповідь 4. Виявлено першопричину: селектор Zustand повертав новий
об’єкт на кожному рендері – «useAuthStore((s) => ({ user: s.user, setUser:
s.setUser, logout: s.logout }))». Оскільки Zustand порівнює результат селектора через
«Object.is», новий об’єкт щоразу вважався зміненим, що породжувало нескінченний
цикл повторного рендерингу і помилку React «Maximum update depth exceeded».
Виправлено розбиттям на три окремі виклики: «useAuthStore((s) => s.user)»,
«useAuthStore((s) => s.setUser)», «useAuthStore((s) => s.logout)». Така сама схема вже
застосовувалася в усіх інших сторінках застосунку.
