                          3 ОПИС ВИКОНАНОЇ РОБОТИ

      3.1 Стратегія масштабування

      Обрано горизонтальне масштабування – запуск кількох ідентичних копій
серверного процесу, що паралельно обробляють запити від різних користувачів.
Підхід базується на ключовій властивості архітектури LumiRum: сервер не зберігає
стан між запитами.
      Автентифікація реалізована через JWT-токени, що перевіряються статично за
криптографічним підписом без звернення до бази даних чи розподіленого кешу.
Будь-яка репліка здатна обробити запит будь-якого користувача без синхронізації
з іншими репліками. Єдиним спільним ресурсом є база даних PostgreSQL, що
забезпечує консистентність стану всієї системи.
      Горизонтальне масштабування реалізовано засобами Docker Compose з Caddy
як балансувальником навантаження.

      3.2 Технічні рішення

      3.2.1 Масштабування з Docker Compose

      Для того щоб Docker Compose міг запускати кілька реплік одного сервісу,
відкриття портів (ports) видалено зі служби «server» – воно б конфліктувало при
спробі прив’язати кілька контейнерів до одного й того самого порту хоста. Весь
вхідний трафік маршрутизується виключно через балансувальник.

 1 server:
 2   build:
 3     context: server
 4     dockerfile: Dockerfile
 5   environment:
 6     DATABASE_URL: postgres://postgres:password@database:5432/data
 7     BIND_ADDRESS: "0.0.0.0:3000"
 8     JWT_SECRET: "change-me-in-production"
 9   depends_on:
10     database:
11       condition: service_healthy


      Запуск із заданою кількістю реплік виконується командою «docker compose
up -d --scale server=N»

        3.2.2 Балансувальник навантаження Caddy

        Caddy виконує функції статичного файлового сервера для SPA та зворотного
проксі для API. Використовується внутрішній DNS в Docker: ім’я «server:3000»
розпізнається у набір A-записів – по одному для кожної репліки, – і Caddy
автоматично балансує запити між ними методом round-robin.

    1 :80 {
    2     @api path /auth* /devices* /profiles* /telemetry* /users* /
      health* /stats*
 3        handle @api {
 4            reverse_proxy server:3000
 5        }
 6        handle {
 7            root * /srv
 8            try_files {path} /index.html
 9            file_server
10        }
11    }
12    :3000 {
13        reverse_proxy server:3000
14    }


        Слухач на порту 3000 виконує функцію «чистого» API-шлюзу без SPA-
фолбеку та використовується Locust для навантажувального тестування бекенду без
участі фронтенду.

        3.2.3 Justfile

        Для зручності запуску визначено Just рецепти з опціональним аргументом
replicas:

1    up replicas="1":
2        docker compose up -d --scale server={{replicas}}
3
4    locust:
5        locust -f locust/locustfile.py --host http://localhost:3000


        3.3 Аналіз вузьких місць

        Бекенд реалізовано на Rust з асинхронним рушієм Tokio. Кожен HTTP-запит
обробляється у легковісній задачі і майже ніколи не блокує потік ОС. Медіана часу
відповіді для більшості ендпоінтів становить 2–14 мс навіть при 1000 одночасних
                                                                               6
користувачів, що свідчить про те, що серверний процес не є вузьким місцем
системи.
     Аналіз виявив два типи вузьких місць із принципово різною природою.
     Перший – база даних PostgreSQL під час сплесків конкурентних транзакцій
із каскадними видаленнями. Locust видаляє тестові акаунти в кінці тесту: 1000
операцій «DELETE /auth/me» ініціюються майже одночасно, кожна з яких запускає
каскадне видалення пов’язаних пристроїв і телеметрії. Такий сплеск вичерпує
пул з’єднань PostgreSQL, що призводить до помилок 500 на частині запитів. Зі
збільшенням кількості реплік запити на видалення розподіляються між більшою
кількістю серверних пулів з’єднань, зменшуючи конкуренцію за ресурси бази даних
– що пояснює скорочення помилок з 480 до 55.
     Другий – хешування паролів алгоритмом Argon2 під час реєстрації
користувачів. Argon2 є навмисно ресурсоємним та суто CPU-bound: одне хешування
займає 95-99 мс незалежно від кількості реплік. Горизонтальне масштабування
на одній фізичній машині не додає процесорних ядер – воно лише перерозподіляє
наявні між репліками. Як наслідок, «POST /auth/register» демонструє стабільно
однакову медіану ( 99 мс) в усіх трьох тестах, тоді як I/O-bound операції помітно
пришвидшуються. Для масштабування Argon2-навантаження необхідне збільшення
фізичних ресурсів (вертикальне масштабування) або розподіл реплік між різними
машинами.

 Кількість реплік    Помилки «DELETE /auth/me»         Частка помилок, %
           1                     480                         48.00
           2                     317                         31.70
           3                      55                         5.50

     Всі інші ендпоінти (GET, POST) за всіх сценаріїв тестування виконано без
жодної помилки.

     Запит    3.    Необхідно   написати    реалістичний     сценарій   Locust   для
навантажувального тестування IoT-системи. Кожен віртуальний користувач має
реєструватись, логінитись, створювати профіль і пристрій, а потім виконувати
завдання з вагами, що відповідають реальним патернам: запис телеметрії домінує
(IoT-пристрій надсилає дані на кожну подію), читання циркадного розкладу –
другий за частотою запит, решта – фонові запити від клієнтів.
     Відповідь 2. Реалізовано клас «LumirumUser» з «on_start»/«on_stop» для
ізольованих тестових акаунтів. Завдання отримали ваги: «POST /telemetry» – 8,
«GET /profiles/circadian/:id» – 4, «GET /devices» та «GET /profiles» – по 2, «GET /
telemetry» та «GET /auth/me» – по 1. Телеметрія надсилається з заголовком «x-api-
key» (ключ пристрою), решта запитів – з «Authorization: Bearer» (JWT). «on_stop»
видаляє акаунт через «DELETE /auth/me».
     —
     Запит 3. Під час тестування виникає «KeyError: 'token'» при ініціалізації
користувача – реєстрація повертає 422, логін не знаходить акаунт. Ім’я користувача
формується як «f"load_{uuid.uuid4().hex[:12]}"».
     Відповідь 3. Виявлено причину: API вимагає суто буквено-цифрові імена
користувачів, а знак підкреслення «_» у шаблоні «load_xxxx» не проходив
валідацію. Виправлено на «f"load{uuid.uuid4().hex[:12]}"».
